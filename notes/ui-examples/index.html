▣ capwrap — spawn UI examples

Three static mocks of one operator moment: spawning an agent while a question waits in the inbox. They reuse the live console's palette, controls and words; only the structure changes. Compare against the live app at http://127.0.0.1:8420. Nothing here talks to the daemon.

What the current console gets wrong

  • The spawn dialog stacks Role, Persona, Agent, Project, Routing and Preset in one column, with a paragraph under Routing and another under Preset. The config preview starts below the fold, so the operator picks values without seeing the config that will run.
  • The two paragraphs overlap: both explain what auto does. Together they take more room than the six controls they explain.
  • The Questions card shows the question and its yes/no chips, then dumps the raw JSON of the ask underneath. The JSON repeats what the header and the chips already say, and reads as noise next to the reply box.

The examples

Example A — same console, rebuilt spawn sheet

Keeps the three-pane console. The spawn dialog becomes a sheet scoped to the working area, so the inbox stays lit and readable while you spawn. Inside, the picks sit left and the config preview sits right at full height: the TOML that will actually run is on screen from the first click, and editing it never pushes the picks away. Routing and Preset become segmented controls sharing one quiet line instead of two paragraphs. The raw JSON on the question card collapses behind a disclosure.

Example B — spawn as three steps: who, where, how it asks

Replaces the field wall with three steps, each one screen tall. Finished steps collapse into their picks inside the stepper, so on the last step you still see who and where without re-reading a form. Routing and preset sit together on step 3 because they are one decision: how much the agent settles on its own. The config preview is a rail beside every step, so it updates as you go instead of appearing at the end.

Example C — one crew surface, spawn as an empty seat

Drops the dialog and the wizard. Every agent is a card on one surface; a pending question sits on the card of the agent that asked, and spawning is an empty seat in the same grid. The spawn form is a sentence with inline picks, so the config reads as intent in the order you think it. The question card says in one line what answering does, and keeps the raw payload behind a disclosure instead of using it as the explanation.

Words and controls are the live app's: role, persona, agent, project, routing (forward / block / auto), preset (standard / autonomous), model, custom instructions, config preview, Approvals and Questions. Autonomous answers plain questions only; permission requests still card, and opencode v1 keeps its permission prompts in its own TUI. There is no mode that auto-approves permissions.
